ELMS: Cursor vs IBM Bob

Two AI agents built the same React + Spring Boot + PostgreSQL leave system from one BRD. This report compares them on business-rule compliance, code quality, performance, security and delivery. Every finding below was checked against the running applications or the source, and each one links to its evidence.

Verdict

Cursor's build is the one that works end to end. IBM Bob's build has the better deployment setup and a richer data model, but its core approval flow fails most of the time.

Recommended baseline

Cursor

11 pass3 partial0 fail
  • The full request → approve → balance → cancel cycle works in the API and the UI.
  • Clean layering: DTOs at every boundary, explicit fetch joins, Open-Session-in-View off.
  • Seeded demo for every role. Balances are created automatically for new hires.
  • Main gaps: deactivated users keep access until their token expires, HR can approve any request, and configuration is hard-coded with no migrations or tests.
Needs fixes before use

IBM Bob

9 pass3 partial2 fail
  • Manager approve/reject returned HTTP 500 in 55 of 61 attempts. The request stays pending.
  • A manager can approve their own leave once HR sets them as their own manager.
  • Policies and Audit Logs pages show empty tables because both APIs return 500.
  • Strengths: Docker Compose for the full stack, Flyway migrations, environment-based config, TypeScript, pessimistic locking and an adjustment-history table.

The rule tallies count the 14 BRD rules from the rule matrix. "Partial" means the rule holds in normal use but breaks in an edge case we reproduced, such as concurrent submits.

The runtimes are not identical. Cursor's API ran on the host JVM (mvn spring-boot:run), while IBM's ran inside Docker Desktop, which adds network and CPU overhead. Treat the throughput gap as indicative. The code-level causes are clearer: Cursor fetch-joins its list queries. IBM's read methods have no transaction and depend on Open-Session-in-View for lazy loading, which Spring warns about at startup. Cursor's user list has an N+1 query (D-C7), which is why it is slower on that one endpoint.

Method & reproducibility

What was run

  • Static review of every backend service, controller, repository, security and config file, plus each frontend's routing, API layer and forms.
  • API verification with comparison/verify/verify.mjs: the same scenarios through each app's own endpoints, using fresh users for each run.
  • Follow-up checks: approve-repeat.mjs, retry-decide.mjs and selfapprove.mjs (D-I1, D-I2), holiday.mjs (RULE-13), rule11-ibm.mjs (RULE-11). Database state was confirmed with psql.
  • Screenshots with screenshots.mjs (Playwright driving local Chrome). manifest.json in each folder records the banner text and browser validation messages.
  • Static checks: tsc --noEmit, oxlint, react-scripts test, bundle sizes with gzip.

Caveats

  • The IBM decision failure rate depends on timing. Across 61 attempts, 6 committed (10%). The cause is deterministic: shared Hibernate session access from @Async threads.
  • Test users (*@verify.test, demo.*@elms.com) and their requests remain in both demo databases. A temporary 2026 holiday row and a temporary leave type were added to IBM's database and then deleted.
  • The IBM backend container was restarted once to rule out degradation over uptime. Failures continued after the restart.
  • The performance numbers come from different runtimes (host JVM vs Docker) and are indicative only.
  • Build-time and token figures come from each tool's own report and were not measured here.
